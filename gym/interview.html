1. Императивный и декларативный код

Чем цикл Go отличается от запроса SQL с тем же результатом?

for _, e := range events {
    if e.Active { active = append(active, e) }
}
SELECT id FROM events WHERE active;
Сверить ответ

Результат. Активные события.

Почему так происходит

Императивный код описывает шаги: обойти, проверить и добавить. Декларативный запрос описывает условие результата. PostgreSQL может поменять физический план, например применить индекс вместо полного сканирования, сохранив смысл запроса.

Если изменить условие. Без ORDER BY SQL не гарантирует порядок выдачи. Цикл по срезу сохраняет порядок входа, если добавляет события сразу. При переносе фильтра в БД отдельно задай порядок, если он входит в контракт.

В бэкенде. Фильтруй события в SQL, когда это уменьшает объём передачи. Go-цикл удобен для правил, использующих уже загруженные данные или внешний контекст.

2. Type switch

Что выведут inspect(&Writer{}) и inspect(Writer{})? Как компилятор проверяет контракт? Что произойдёт при замене *Writer на Writer в проверке?

type Writer struct{}
func (*Writer) Write(p []byte) (int, error) { return len(p), nil }

var _ io.Writer = (*Writer)(nil)

func inspect(v any) {
    switch x := v.(type) {
    case io.Writer:
        n, _ := x.Write([]byte("Go"))
        fmt.Println(n)
    default:
        fmt.Println("unknown")
    }
}
Сверить ответ
  1. Конкретный тип
  2. →интерфейс
  3. →проверка динамического типа

Ответ. inspect(&Writer{}) → 2; inspect(Writer{}) → unknown.

Почему. У метода pointer receiver, поэтому проверка с Writer{} не скомпилируется. Type switch работает с динамическим типом значения интерфейса. Встраивание продвигает методы, но не превращает внешний тип в подтип вложенного.

В бэкенде. Определи маленький интерфейс рядом с сервисом-потребителем, например EventReader. Адаптер PostgreSQL удовлетворит ему своим набором методов.

Почему Go так работает

any позволяет передать оба значения. Внутри интерфейса Go сохраняет конкретный тип и значение. В первом вызове конкретный тип *Writer имеет нужный метод Write, поэтому подходит ветка io.Writer. Во втором вызове конкретный тип Writer имеет другой набор методов, поэтому выполняется default.

Если изменить условие. Для адресуемой переменной w компилятор может преобразовать w.Write(p) в (&w).Write(p). При присваивании интерфейсу эта подстановка не выполняется. Чтобы оба типа прошли проверку, в этом примере можно объявить метод с получателем Writer, если ему достаточно работать с копией.

3. Проверка реализации интерфейса

Зачем эта строка, если Go и так проверяет интерфейсы?

type EventReader interface { ReadID() string }
type Repo struct { ID string }
func (r *Repo) ReadID() string { return r.ID }
var _ EventReader = (*Repo)(nil)
Сверить ответ

Результат. Сборка проходит.

Почему так происходит

Компилятор проверяет набор методов типа и их сигнатуры. Присваивание пустому идентификатору делает проверку явной рядом с адаптером. Значение (*Repo)(nil) нужно здесь только для указания типа. Метод на нём не вызывается.

Если изменить условие. При замене выражения на Repo{} сборка упадёт: метод объявлен на *Repo. Возможность вызвать метод на адресуемой переменной Repo через автоматическое взятие адреса не добавляет метод в набор методов Repo.

В бэкенде. Проверяй соответствие реализации контракту репозитория при сборке, даже если конкретный адаптер в этом тесте ещё не используется.

4. Как работает append

Что напечатает код? Что изменится, если ограничить ёмкость первого среза через a[:1:1]?

a := []int{10, 20, 30}
b := append(a[:1], 99)
var empty []int
fmt.Println(a, b, empty == nil, len(empty), cap(empty))
Сверить ответ
  1. Исходный массив
  2. →два среза
  3. →запись в общий массив

Ответ. [10 99 30] [10 99] true 0 0

Почему. В a[:1] есть место до конца backing array. append записывает 99 по индексу 1. При a[:1:1] ёмкости не хватает и append возвращает срез с новым массивом. Nil-срез можно обходить, срезать до [:0] и передавать в append. Индексация [0] вызовет panic.

В бэкенде. Фильтрация событий. Если исходный список ещё нужен, собирай выход в отдельном срезе.

Почему Go так работает

a и b держат каждый своё описание среза, но описания могут указывать на один и тот же массив. В описании есть адрес первого элемента, длина len и ёмкость cap. Индекс 1 у обоих срезов означает вторую ячейку того же массива, потому что начальный адрес у них общий.

Что находится в памяти
МоментЯчейка 0Ячейка 1Ячейка 2
До append102030
После append109930
  1. a[:1] смотрит на ячейку 0. Длина равна 1, ёмкость равна 3. Это значит, что срез пока видит один элемент, но может вырасти ещё на два.
  2. append добавляет элемент по индексу, равному старой длине. Здесь индекс 1 укладывается в ёмкость, поэтому 99 записывается поверх 20 в существующем массиве.
  3. b получает описание длиной 2. Длина a остаётся 3. Когда читаем a[1] и b[1], оба обращения идут в ячейку 1 и возвращают 99.

Если изменить условие. У a[:1:1] ёмкость равна 1, поэтому второй элемент туда не помещается. append создаст новый массив, перенесёт 10 и добавит 99. Тогда a останется [10 20 30], а b будет [10 99]. Само выражение a[:1:1] всё ещё делит память с a. Например, запись a[:1:1][0] = 7 изменит a[0].

5. Нулевое значение среза

Какие операции с nil-срезом безопасны и чем два вызова append отличаются?

var s []string
a := append(s, []string(nil)...)
b := append(s, "")
fmt.Println(s == nil, a == nil, len(b))
Сверить ответ

Результат. true true 1.

Почему так происходит

Nil-срез уже описывает пустую последовательность. len и cap дают 0, range делает ноль итераций, s[:0] допустим, copy из него копирует ноль элементов. append с нулём элементов возвращает исходный срез. Добавление пустой строки выделяет место под элемент.

Если изменить условие. Чтение s[0] вызовет panic. Пустой ненулевой []string{} тоже имеет длину 0, но encoding/json обычно кодирует его как [], а nil-срез — как null.

В бэкенде. Если поле списка в API должно быть массивом, проверь результат сериализации пустой выдачи.

6. Как устроена map

Зачем после вычисления хеша Go всё равно проверяет исходный ключ?

m := map[string]int{"a": 0}
m["b"] = 2
x, ok := m["a"]
fmt.Println(x, ok)
Сверить ответ

Результат. 0 true.

Почему так происходит

Хеш сужает поиск. Разные ключи могут давать одинаковый хеш или одно место для поиска, поэтому принадлежность проверяют сравнением самих ключей. Начиная с Go 1.24 реализация map основана на Swiss Tables: метаданные группы помогают быстро отсеять неподходящие позиции.

Если изменить условие. Равенство хешей не означает равенство строк. Для map общего доступа синхронизируй записи и чтение при наличии писателей. Паника runtime в некоторых случаях конкурентного доступа не заменяет детектор гонок.

В бэкенде. Map подходит для дедупликации ID и подсчёта статусов. При объяснении разделяй контракт языка и детали конкретной версии runtime.

7. Порядок обхода map

Можно ли опираться на порядок вставки? Что гарантирует пример ниже?

m := map[string]int{"b": 2, "a": 1}
keys := make([]string, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
slices.Sort(keys)
fmt.Println(keys, m["missing"])
Сверить ответ
  1. Ключ
  2. →поиск записи · ключи
  3. →сортировка
  4. →выдача

Ответ. [a b] 0

Почему. Порядок range по map не определён. Сортировка отдельного среза делает выдачу стабильной. Отсутствующий ключ даёт zero value, а второй результат чтения сообщает, был ли ключ. В Go 1.24 появилась реализация map на Swiss Tables. Детали внутреннего устройства привязывай к версии.

В бэкенде. Сортируй ключи перед формированием стабильного отчёта или последовательным обходом узлов.

Почему Go так работает

Поиск и обход решают разные задачи. Для m["a"] Go вычисляет хеш ключа, находит возможное место в таблице и проверяет сам ключ. При range он перечисляет существующие записи. Внутреннее размещение не хранит для тебя порядок вставки, а спецификация позволяет менять порядок обхода даже между двумя проходами.

Если изменить условие. И map[string]int{"x": 0}, и пустая map дают 0 при чтении m["x"]. Разницу покажет v, ok := m["x"]: (0, true) и (0, false). Сортировка гарантирует порядок только для среза keys. Для упорядоченной выдачи обходи этот срез и читай m[k].

8. Чтение из закрытого канала

Какие пары вернут два чтения? Что случится при отправке после close?

ch := make(chan int, 1)
ch <- 7
close(ch)
a, okA := <-ch
b, okB := <-ch
fmt.Println(a, okA, b, okB)
Сверить ответ
  1. close
  2. →дочитать буфер
  3. →zero value и ok=false

Ответ. 7 true 0 false

Почему. Закрытие сохраняет уже отправленные значения. После опустошения буфера чтение возвращает нулевое значение и false. Отправка в закрытый канал вызывает panic. В fan-in выход закрывает координатор после завершения всех отправителей.

В бэкенде. При отмене подписки останавливай отправителей через context, чтобы исключить запись после закрытия выхода.

Почему Go так работает

У буферизованного канала есть очередь значений и признак закрытия. ch <- 7 кладёт число в очередь. close(ch) меняет признак закрытия. Первое чтение находит число в очереди и возвращает (7, true). Второе видит пустую очередь и закрытие, поэтому ждать отправителя бессмысленно: оно сразу выдаёт (0, false).

Если изменить условие. При отправке 0 первое чтение вернуло бы (0, true). Смотри на ok, чтобы отличить значение от конца потока. Из открытого пустого канала чтение, наоборот, ждёт отправителя.

9. Отправка в закрытый канал

Почему после close отправитель получает panic, а не ошибку?

ch := make(chan int, 1)
close(ch)
ch <- 7
Сверить ответ

Результат. panic: send on closed channel.

Почему так происходит

close объявляет завершение отправки. У операции ch <- v нет возвращаемого error. После закрытия отправка считается ошибкой программы и вызывает panic. То же относится к повторному close.

Если изменить условие. Нельзя безопасно проверить открытость канала, а потом отдельно отправить: между проверкой и отправкой другая горутина может закрыть его. default в select не спасает от выбранной отправки в закрытый канал.

В бэкенде. При нескольких отправителях координатор ждёт их завершения и только потом закрывает выход. Читатель сообщает об отмене через context.

10. Сортировка структур по имени

Что изменится в исходном массиве после сортировки a[:]?

a := [2]User{{Name: "Zoe"}, {Name: "Ann"}}
slices.SortFunc(a[:], func(x, y User) int {
    return strings.Compare(x.Name, y.Name)
})
fmt.Println(a[0].Name)
Сверить ответ

Результат. Ann.

Почему так происходит

slices.SortFunc переставляет элементы переданного среза. a[:] не копирует данные массива, поэтому запись через срез меняет a. Компаратор возвращает отрицательное число, ноль или положительное число по тому, как соотносятся имена.

Если изменить условие. При одинаковом Name SortFunc не обещает сохранить исходный порядок. Используй SortStableFunc, если нужно сохранить его, или добавь ID в компаратор для полного порядка.

В бэкенде. Проверь сравнение имён по контракту продукта. strings.Compare сравнивает байты строки и сам по себе не учитывает локальные правила алфавита.

12. Разворот односвязного списка

Разверни 1 → 2 → 3. Почему нужно сохранить cur.Next до записи?

func reverse(head *Node) *Node {
    var prev *Node
    for cur := head; cur != nil; {
        next := cur.Next
        cur.Next = prev
        prev, cur = cur, next
    }
    return prev
}
Сверить ответ
  1. next сохраняем
  2. →ссылку разворачиваем
  3. →двигаемся дальше

Ответ. 3 → 2 → 1. Время O(n), дополнительная память O(1).

Почему. Сохраняем ссылку на хвост до изменения Next. Проверь nil, один узел и несколько узлов.

В бэкенде. Когда обработчик разворачивает цепочку на месте, её прежний порядок изменится и для других владельцев тех же узлов.

Почему Go так работает

cur указывает на сам узел, поэтому cur.Next = prev меняет связь в списке. На первом шаге prev == nil. Если сразу записать это значение в 1.Next, связь 1 → 2 исчезнет. Сохранённый next остаётся адресом узла 2, так что обход можно продолжить.

Если изменить условие. Если сохранить next после изменения cur.Next, на первом шаге он уже будет nil, и цикл вернёт только узел 1. У пустого списка тело цикла вообще не выполняется, а один узел остаётся головой.

14. Как различать ошибки

Какая проверка распознает причину после добавления контекста?

fmt.Println(err == temporary, errors.Is(err, temporary))
Сверить ответ
  1. Причина
  2. →обёртка с контекстом
  3. →решение вызывающего кода

Ответ. false true

Почему. Прямое сравнение видит обёртку. errors.Is ищет причину в цепочке. errors.As извлекает ошибку заданного типа. Возможность повтора зависит от операции, лимита попыток, дедлайна и идемпотентности. У net.Error проверяй Timeout, Temporary помечен deprecated.

18. Один буфер в нескольких горутинах

Два среза разделяют массив. Каким будет результат после записи? Где нужна синхронизация?

  2. →независимая копия
  3. →обработчик

Почему. Если одна горутина пишет, а другая читает те же байты без синхронизации, возможна гонка. После безопасной публикации неизменяемый буфер можно читать совместно. 21. Диагностика задержек в проде

HTTP duration p99: 250 ms → 510 ms

CPU: примерно без изменений
Сверить ответ

  2. →найти медленный участок
  3. →выбрать профиль

Ответ. Начни с метрик ожидания пула и трассировки медленных запросов.

Почему. Сначала локализуй путь по метрикам запроса и traces. Для нагрузки на CPU бери CPU-профиль, для памяти — heap или allocs, для ожиданий — block/mutex profiles либо execution trace по симптомам. У профилирования есть накладные расходы. Их величина зависит от типа профиля, настроек и нагрузки.

В бэкенде. На ListEvents проверь длительность запроса, ожидание соединения и захват блокировок. Сопоставь p99 с изменением после релиза.

Как разбирать метрики

Запрос может ждать свободного соединения и в это время почти не расходовать CPU. При чтении p50 виден типичный запрос. p99 показывает, как долго ждут запросы у верхней границы распределения. Поэтому обе метрики могут двигаться по-разному.

Как отличить причины. Если в trace растёт интервал до получения соединения, смотри ожидания пула. Если соединение выдали сразу, а растёт интервал выполнения SQL, смотри запрос и блокировки БД. Если задержка выросла внутри вычислительного участка и этот участок грузит процессор, CPU-профиль покажет, где тратится время.

25. Embedding и наследование

Почему p.Read() доступен, но Profile нельзя передать как Base?

type Base struct{}
func (Base) Read() {}
type Profile struct { Base }
var _ interface{ Read() } = Profile{}
Сверить ответ

Результат. Profile реализует Read.

Почему так происходит

Embedding — композиция. Go разрешает сократить доступ к полю или методу, например p.Read() вместо p.Base.Read(). Вызов метода Base по-прежнему получает Base как receiver.

Если изменить условие. Если Profile объявит собственный Read, обычный вызов p.Read выберет внешний метод. Вызовы из методов Base не начнут динамически переадресовываться наружу. Profile и Base остаются разными типами.

В бэкенде. Встраивание может упростить композицию типов. Для взаимозаменяемости адаптеров используй интерфейс с нужными методами.

28. Границы Go и преобразование срезов

Почему []io.ReadWriter нельзя присвоить []io.Reader? Почему поэлементное присваивание работает?

func readers(in []io.ReadWriter) []io.Reader {
    out := make([]io.Reader, len(in))
    for i, rw := range in {
        out[i] = rw
    }
    return out
}
Сверить ответ
  1. Один алгоритм
  2. →разные конкретные типы · каждый элемент преобразуем явно

Ответ. Прямое присваивание срезов не компилируется. Поэлементное присваивание допустимо.

Почему. Go делает преобразование интерфейсных срезов явным. Если тебе нужна жёсткая гарантия верхней границы задержки, проверь, подходят ли планировщик, GC и системные зависимости под требования. Генерики есть начиная с Go 1.18, поэтому их отсутствие к ограничениям современного Go не относится.

В бэкенде. Типизированный helper дедупликации подходит для ID нескольких типов. При преобразовании интерфейсных срезов учитывай дополнительный проход и аллокацию.

Почему Go так работает

[]io.ReadWriter и []io.Reader обещают разные возможности для каждого элемента. Представь, что один массив доступен через оба среза. Через []io.Reader можно записать туда объект, у которого есть только Read. Тогда вызов Write через исходный срез потерял бы гарантию. Go отвергает такое присваивание срезов.

Если изменить условие. Присваивание одного элемента разрешено, потому что io.ReadWriter уже включает Read. Новые ячейки среза независимы. Если оба интерфейсных значения содержат один и тот же *bytes.Buffer, чтение через одно продвигает позицию того же буфера для второго.
